SQL EVIDENCE - VIOLATION 1: SESSIONS BEFORE REGISTRATION
================================================================================

Query:
SELECT 
    COUNT(*) as total_violations,
    COUNT(*) FILTER (WHERE datediff('day', p.first_seen_date, us.timestamp) < -180) 
        as more_than_6_months_early,
    MIN(datediff('day', p.first_seen_date, us.timestamp)) as earliest_violation_days,
    ROUND(AVG(datediff('day', p.first_seen_date, us.timestamp)), 2) as avg_days_before
FROM user_sessions us
INNER JOIN people p ON us.person_id = p.person_id
WHERE us.timestamp < p.first_seen_date

Results:
Total violations:        7,412 (49.5% of 14,964 sessions)
>6 months early:         1,895 (25.6%)
Earliest violation:      -361 days (11.8 months)

WHY VIOLATIONS CAN'T BE FIXED (without FR #2)
================================================================================

ROOT CAUSE: TEMPORAL DECOUPLING IN GENERATION

Current Architecture (v1.1):
1. Parent tables (people, campaigns, companies, etc.)
   - Generated with their own timestamp logic
   - No temporal metadata exported

2. Child tables (user_sessions, mentions, transactions, etc.)
   - Generated from FIXED absolute date ranges [2024-01-01, 2024-12-31]
   - No awareness of parent table timestamps
   - No FK constraint on timestamps
   - Each record generated independently in isolation

3. Result: Independent timelines
   - Parent and child timelines don't intersect
   - 48% of records violate logical timeline

THE PROBLEM IN DETAIL:

CURRENT (BROKEN):
  user_sessions.timestamp: [2024-01-01, 2024-12-31]  ← Random generation
                                     ↑
                                     ↓
           person.first_seen_date: [2024-06-15, 2024-12-31]
           
  Result: 49.5% sessions before person exists!

NEEDED (FR #2):
  person.first_seen_date: [2024-06-15, 2024-12-31]  ← First generated
                                     ↓ (use this!)
  user_sessions.timestamp: [first_seen_date, first_seen_date + 365d]
  
  Result: 100% sessions after person registration

Why Current Fix Attempts Fail:
1. Temporal decoupling: Child records don't know parent timestamps
2. Generation order: Both tables generated independently, no pipeline
3. Range binding: Each table has absolute hardcoded date ranges
4. No metadata: Generator doesn't track parent temporal boundaries
5. Stateless generation: Each record generated in isolation

FR #2 REQUIREMENT: PARENT-REFERENCED TIMESTAMPS
================================================================================

WHAT FR #2 MUST PROVIDE:
"When generating child records, dynamically reference parent timestamps"

1. SESSIONS -> PEOPLE
   Fix: session.timestamp >= person.first_seen_date
   Impact: Eliminates 7,412 violations (49.5%)

2. MENTIONS -> CAMPAIGNS
   Fix: mention.timestamp >= campaign.start_date
   Impact: Eliminates 1,289 violations (42.4%)

3. TRANSACTIONS -> COMPANIES
   Fix: transaction.timestamp >= company.signed_date
   Impact: Eliminates 773 violations (50.4%)

4. ENGAGEMENT -> POSTS
   Fix: engagement.timestamp >= post.posted_at
   Impact: Eliminates 4,694 violations (48.0%)

5. TICKETS (self-referential)
   Fix: resolved_at >= created_at
   Impact: Eliminates 1,406 violations (47.9%)
